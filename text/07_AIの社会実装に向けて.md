# 07 AIの社会実装に向けて

> 技術分野だが、技術そのものではなく「AIを実際のビジネスや社会で使えるようにするまでの進め方」の章。計算や仕組みの理解より、**プロセスの順番・用語の対応・よくある失敗の原因**が問われる。法律と契約の詳細は09章、倫理とガバナンスは10章で扱う。

## この章で押さえること

- AIプロジェクトは **「課題を決める → データを集める → モデルを作る → PoCで確かめる → 本番に組み込む → 運用しながら直す」** の流れで進む。作って終わりではなく、**運用（監視と再学習）まで含めて1つのサイクル**になる。
- 標準プロセスは **CRISP-DM**（6工程。最初は「ビジネス理解」）。機械学習向けに品質保証と**監視・保守**を加えたのが **CRISP-ML(Q)**、運用を仕組み化する考え方が **MLOps**。
- AIの精度は**データの質と量**で決まる。アノテーションのコスト、**サンプリングバイアス**、**データリーケージ**が「データの落とし穴」の代表。
- 実行環境は **クラウド**（大きな計算力）と**エッジ**（リアルタイム・通信不要・プライバシー）を使い分ける。運用中はデータの変化（**ドリフト**）で精度が落ちるので、監視と再学習が要る。

## 全体像: AIプロジェクトのライフサイクル

```
[企画]   課題の決定・ステークホルダーの整理・BPR（業務の作り直し）
   │      └ 「AIで何かやりたい」ではなく「どの課題を解くか」から始める
   ▼
[データ] 収集（自社データ・オープンデータセット・コーパス）
   │      → アノテーション（正解ラベル付け）→ 前処理
   │      └ 落とし穴: サンプリングバイアス、データリーケージ
   ▼
[開発]   モデリング（Python、Jupyter Notebook）→ 評価
   │      └ PoC（概念実証）で「本当に効果が出るか」を小さく確かめる
   ▼
[実装]   本番環境へ組み込み（クラウド／エッジ、API、Docker）
   ▼
[運用]   モニタリング → ドリフトを検知 → 再学習 → 再デプロイ
   │      └ この繰り返しを自動化・仕組み化するのが MLOps
   └────→ 必要に応じて前の工程へ戻る（CRISP-DM の反復）
```

## 7-1 AIプロジェクトの計画と進め方

### AIプロジェクトの進め方（3つの要素）
- **一言で**: AIプロジェクトを成功させるには **「AI人材の育成・確保」「課題の決定」「データの確保」** の3つがそろう必要がある。
- **なぜ強調されるか**: 「流行っているからAIで何かやりたい」と手段から入ったプロジェクトは、解くべき課題がはっきりせず失敗しやすい。また、良いデータは急には集まらないので、**初期の段階からデータ収集を始める**必要がある。
- **問われ方**: 「AIプロジェクトの最初にやるべきこと」→ 解決したい**課題（目的）を明確にする**。「まずモデルを作ってみる」「最新の手法を選ぶ」は誤りの選択肢になりやすい。

### AIのビジネス活用で注意すること
- **一言で**: 精度だけでなく、**法令順守・倫理・公平性**に配慮しないと事業として成り立たない。
- **代表例**: Amazonが開発していた採用AIが、過去の応募者（技術職は男性が多い）のデータから学んだ結果、**女性を不利に評価する偏り**を持ってしまい、2018年に開発の中止が報じられた。データの偏りが差別につながる事例として頻出（→ 10章）。
- **監視カメラの例**: 顔画像そのものを保存し続けるのではなく、必要な特徴量だけを取り出して元画像を破棄する、利用目的を掲示する、といったプライバシーへの配慮が求められる（個人情報保護法は → 09章、カメラ画像利活用ガイドブックは → 10章）。

### BPR（ビジネスプロセス・リエンジニアリング）
- **一言で**: 業務の流れ・組織・情報システムを**根本から作り直す**業務改革。1990年代初めにマイケル・ハマーらが提唱した。
- **AIとの関係**: 今の業務手順をそのままにAIを「付け足す」だけでは効果が限られる。AIがあることを前提に、**仕事のやり方そのものを再設計する**発想が必要、という文脈で出題される。
- **違い**: 業務改善（今のやり方を少しずつ良くする）に対して、BPRは**ゼロベースの抜本的な見直し**。

### CRISP-DM と CRISP-ML(Q)

**CRISP-DM**（Cross-Industry Standard Process for Data Mining）は、業界を問わず使える**データ分析プロジェクトの標準プロセス**。1990年代後半に企業連合が作り、2000年に公開された。

```
 ① ビジネス理解 ⇄ ② データ理解
        ↓
     ③ データ準備 ⇄ ④ モデリング
        ↓
     ⑤ 評価 ──（不十分なら①に戻る）
        ↓
     ⑥ 展開（デプロイメント）
```

- **最初は「ビジネス理解」**（データ理解ではない）。ここで「何を達成すれば成功か」を決める。
- 一方向に進むのではなく、**必要に応じて前の工程に戻る反復型**のプロセス。
- 全工程の中で、データ準備（前処理）が最も時間がかかることが多い。

**CRISP-ML(Q)** は、CRISP-DM を**機械学習プロジェクト向け**に拡張したもの（2020年に Mercedes-Benz AG などの研究者が提案）。末尾の **Q は Quality（品質保証）**。

| 項目 | CRISP-DM | CRISP-ML(Q) |
|---|---|---|
| 対象 | データ分析全般（データマイニング） | 機械学習の開発・運用 |
| 工程数 | 6 | 6 |
| 最初の工程 | ビジネス理解、データ理解（別工程） | ビジネス理解とデータ理解を**1つにまとめる** |
| 最後の工程 | 展開（デプロイメント） | **監視と保守**（Monitoring and Maintenance）を追加 |
| 特徴 | 反復型 | 各工程でリスクを洗い出し、**品質保証**の手法を定める |

- **なぜ CRISP-ML(Q) が必要になったか**: 機械学習のモデルは、デプロイした後も**現実のデータが変わると精度が落ちる**（7-4のドリフト）。CRISP-DM は展開で終わるため、運用後の監視・保守を扱えなかった。
- **問われ方**: 「CRISP-DM の最初の工程」→ ビジネス理解。「CRISP-ML(Q) の Q の意味」→ Quality（品質保証）。

### PoC（概念実証）
- **一言で**: 本格開発の前に、**小さく試して実現可能性と効果を確かめる**工程。
- **なぜ**: AIは「やってみないと精度が出るかわからない」技術。いきなり大規模に投資すると、精度が出なかったときの損失が大きい。
- **進め方**: 目的・検証方法・合否の基準を決める → 実際に試作して検証する → 結果を評価し、本開発に進むか決める。
- **PoC止まり（PoC疲れ）**: PoCを繰り返すだけで本番導入に至らない問題。原因は、成功の基準があいまい、業務への組み込み方を考えていない、現場や経営層を巻き込んでいない、など。
- **契約との関係**: 経済産業省の「AI・データの利用に関する契約ガイドライン」は、**アセスメント → PoC → 開発 → 追加学習**の**探索的段階型**で進めることを勧め、PoC 段階では導入検証契約を結ぶ（→ 09章）。

### アジャイルとウォーターフォール

| | ウォーターフォール | アジャイル |
|---|---|---|
| 進め方 | 要件定義 → 設計 → 実装 → テストを**順番に1回**。原則として後戻りしない | 計画〜テストの**小さなサイクルを何度も繰り返す** |
| 強み | 全体のスケジュール・コストを管理しやすい | **仕様変更に柔軟**、利用者の要望を取り込みやすい |
| 弱み | 途中の変更や問題に弱い（後工程で見つかると手戻りが大きい） | 全体の見通しやコストを最初に確定しにくい |
| AI開発との相性 | 作るものが最初から明確な場合向き | 精度が試すまでわからない**AI開発と相性が良い** |

- **問われ方**: 「試行錯誤が多いAI開発に向く手法」→ アジャイル。「工程を順に進め、後戻りしない」→ ウォーターフォール。

### 体制づくり: ステークホルダーと外部との連携
- **ステークホルダー**: 株主・経営者・従業員・顧客・取引先・行政など、事業の**利害関係者**全体。AI導入では、開発者だけでなく**実際にAIを使う現場**や**AIの判断を受ける顧客**も含めて合意を取る。
- **データサイエンティスト**: 統計・IT・ビジネスの知識を組み合わせて、データ分析やモデル作成を担う専門職。3要素の「AI人材」の中核。ほかに、データを整えるデータエンジニア、運用を担うMLエンジニアなどと役割を分けることが多い。
- **オープンイノベーション**: 社外のアイデアや技術を積極的に取り入れて新しい価値を生む手法。自社だけで閉じる**クローズドイノベーション**と対比される。
- **産学連携**: 企業（産）と大学（学）の協力。企業は最新の研究成果と人材を、大学は研究資金と現場のデータを得られる。オープンイノベーションの一形態。
- **他企業や他業種との連携**: 1社でそろわないデータや技術を補える。ただし、**データや学習済みモデルの権利が誰にあるか、利用範囲をどうするか**を事前に契約で決めておかないと紛争になる（→ 09章）。

| 用語 | 一言で | 対になる言葉 |
|---|---|---|
| オープンイノベーション | 社外の知恵を取り込む | クローズドイノベーション |
| 産学連携 | 企業 × 大学 | （オープンイノベーションの一形態） |
| 他企業や他業種との連携 | 企業 × 企業 | 契約（権利帰属・利用条件）に注意 |

## 7-2 データの収集・加工・管理

### データの集め方

| 集め方 | 内容 | 注意点 |
|---|---|---|
| 自社データ | 業務で蓄積したデータ、IoT機器のセンサーデータ | 学習用に集めていないので、形式がばらばら・ラベルがないことが多い |
| **オープンデータセット** | 企業・研究機関・政府が公開する、自由に使えるデータ | **ライセンス**（商用利用の可否など）を確認する |
| **コーパス** | 自然言語処理用に、文章を大量に集めて整理したもの | 偏った文章が多いと、言語モデルも偏る |
| 購入・提携 | データ販売事業者、他社との連携 | 契約で利用範囲を決める（→ 09章） |
| Web からの収集 | クローリング・スクレイピング | 著作権法30条の4、利用規約、個人情報に注意（→ 09章） |

**代表的なオープンデータセット**

| データセット | 中身 |
|---|---|
| MNIST | 手書き数字（0〜9）の画像7万枚（訓練6万・テスト1万）、28×28ピクセル |
| CIFAR-10 | 10クラスの小さなカラー画像6万枚（32×32ピクセル） |
| ImageNet | 約1,400万枚・2万以上のカテゴリの画像。ILSVRC の元データ（→ 02章） |
| MS COCO | 物体検出・セグメンテーション・キャプション用の画像データ |

- 政府のオープンデータ（統計データの e-Stat など）も、需要予測などの補助データとして使える。

### アノテーション
- **一言で**: データに**正解ラベル（タグ）を付けて教師データを作る**作業。画像に「犬」と付ける、物体を枠で囲む、文章に感情（肯定・否定）を付ける、など。
- **なぜ重要か**: 教師あり学習の精度は、ラベルの**質**に直結する。人によって基準がぶれると、モデルもぶれる。
- **課題と対策**:
  - 人手で行うため**時間と費用がかかる** → 外部委託やクラウドソーシングを使う。
  - 作業者ごとに基準がぶれる → **アノテーションの基準（ガイドライン）**を文書化し、複数人の結果を照合する。
  - ラベル付きデータを減らしたい → 半教師あり学習・自己教師あり学習・転移学習（→ 06章）、能動学習（モデルが迷うデータから優先的に人がラベルを付ける）。
- **問われ方**: 「アノテーションのコストを下げる工夫」として、上の手法が選択肢に並ぶ。

### データの偏りとサンプリングバイアス
- **サンプリングバイアス**: データの**集め方（抽出の仕方）**が偏っているせいで、結果が母集団全体を代表しなくなること。例: 大学病院の患者データだけで作ったモデルを、地域の診療所の患者に使う。集めやすい所からだけ集めると起きる。
- **データの偏り**: 学習データの中で、性別・人種・年齢などの属性が不均衡になっていること。Amazonの採用AI（男性に偏った過去データ）や、顔認識の人種による精度差が代表例。
- **関係**: サンプリングバイアスは「偏りが生まれる**原因**（集め方）」、データの偏りは「データに現れた**状態**」と整理するとわかりやすい。どちらも、開発者に差別の意図がなくても不公平な判断を生む。公平性の観点は → 10章。
- **対策**: 対象とする利用者全体を代表するように集める、属性ごとのデータ数と精度を確認する、少ないクラスを増やす（オーバーサンプリング）・多いクラスを減らす（アンダーサンプリング）。

### データリーケージ
- **一言で**: 予測の時点では**本来知り得ない情報**が、学習データに紛れ込むこと（リーク＝漏れ）。
- **なぜ問題か**: 学習・テストでは異常に高い精度が出るのに、本番ではその情報が手に入らないため**精度が大きく下がる**。評価をだましてしまうので気づきにくい。
- **典型例**:
  - 「病気かどうか」を予測するのに、**診断後に処方された薬**の情報を入力に使う。
  - 時系列データをランダムに分割し、**未来のデータで学習して過去を予測**してしまう。
  - テストデータも含めた全体で正規化（平均・標準偏差の計算）をしてから分割する。
- **対策**: 「予測する時点で手に入る情報か」を特徴量ごとに確認する。時系列は時間の順に分割する。前処理の計算は訓練データだけで行う。
- **問われ方**: 「テストの精度は高いのに、本番で精度が大きく落ちた。考えられる原因は」→ データリーケージ（または後述のドリフト）。

### データが足りないときの選択肢
- **転移学習・ファインチューニング**: 別のタスクで学習済みのモデルを土台にし、少ないデータで高精度を出す（詳細 → 06章）。
- **データ拡張**: 画像の回転・反転などで学習データを水増しする（→ 05章）。
- **オープンデータセットや事前学習済みモデル・基盤モデルの利用**（→ 06章）。

### データの管理
- 学習に使ったデータの**出どころと加工の履歴（データの来歴）**、どのデータでどのモデルを作ったか（バージョン管理）を記録しておくと、問題が起きたときに原因を追える（トレーサビリティ・再現性 → 10章）。
- 個人情報を含むデータは、取得時の利用目的の範囲で使い、匿名加工・仮名加工などを検討する（→ 09章）。

## 7-3 開発・運用の環境

### 開発の道具

| 用語 | 一言で | ポイント |
|---|---|---|
| **Python** | AI・機械学習で最もよく使われるプログラミング言語 | 文法が平易で、ライブラリが豊富。scikit-learn（機械学習）、PyTorch・TensorFlow（ディープラーニング）、NumPy・pandas（数値計算・表データ）など |
| **Jupyter Notebook** | ブラウザ上でコードを書いて**すぐ実行**し、結果を確かめられる環境 | コード・実行結果・グラフ・メモを1つのノートに並べて残せる。データ分析の試行錯誤に向く |
| **Docker** | アプリと実行に必要なものを**コンテナ**にまとめて動かす仕組み | 「自分のPCでは動くのに本番では動かない」を防ぐ。仮想マシンより軽量で、開発環境と本番環境をそろえやすい |
| **API** | ある機能を、決められた形式で**外部のプログラムから呼び出せる窓口** | 学習済みモデルをAPIとして公開すれば、他のシステムから予測を呼び出せる。逆に、生成AIなどをAPI経由で自社サービスに組み込める |

- **Docker の補足**: 仮想マシンは OS ごと丸ごと仮想化するので重い。コンテナは OS の中核部分を共有し、アプリとライブラリだけを分けるので軽く、起動が速い。

### クラウドとエッジ

| | クラウド | エッジ（エッジAI） |
|---|---|---|
| 一言で | インターネット越しに、サーバー・ストレージ・計算資源を**必要な分だけ借りる** | スマホ・カメラ・車・工場の機器など**利用者の手元の端末上**でAIを動かす |
| 強み | 大きな計算力（GPU）を使える。初期投資が小さく、規模を柔軟に変えられる | **リアルタイム性**（通信の遅れがない）、**通信不要**でも動く、データを外に出さないので**プライバシー**に有利、通信量を減らせる |
| 弱み | 通信の遅延・通信障害の影響を受ける。データを外部に送る必要がある | 計算資源・電力・メモリが限られる。大きなモデルは動かしにくい |
| 向く処理 | **学習**、大規模なモデルの推論 | 自動運転、工場の異常検知、スマホの顔認証など**即応が必要な推論** |

- **IoT**: 身の回りのモノ（家電、センサー、車、機械）がインターネットにつながる仕組み。IoT機器が集めたデータをクラウドで分析したり、IoT機器上で直接AIを動かしたり（エッジAI）する組み合わせが多い。
- **よくある構成**: クラウドで学習し、軽量化したモデルを**エッジに配って推論**する。エッジで動かすためのモデルの軽量化（蒸留・量子化・プルーニング）は → 06章。
- 代表的なクラウドサービス: AWS（Amazon）、Microsoft Azure、Google Cloud。
- **問われ方**: 「エッジAIの利点として**不適切な**もの」→「大規模なモデルの学習に向く」などが誤り。リアルタイム性・プライバシー・通信量削減が正しい利点。

## 7-4 運用とMLOps

### なぜ運用が難しいのか
普通のソフトウェアは、コードを変えなければ同じ動作を続ける。機械学習のモデルは、**コードを変えなくても、入ってくるデータが変わると性能が落ちる**。そのため「作って終わり」にできない。

### ドリフト（モデルの劣化の原因）

| 種類 | 何が変わるか | 例 |
|---|---|---|
| **データドリフト**（共変量シフト） | 入力データの**分布**が変わる | カメラを新機種に替えて画像の明るさが変わる、新しい客層が増える |
| **コンセプトドリフト** | 入力と正解の**関係そのもの**が変わる | 感染症の流行で「同じ条件でも売れる商品」が変わる、詐欺の手口が変わる |

- **対策**: 運用中の入力データと予測精度を**モニタリング**し、劣化を検知したら新しいデータで**再学習**してモデルを更新する。
- 再学習時は、新しいデータに合わせるあまり過去の知識を忘れる（破壊的忘却 → 06章）ことや、評価をやり直さずに入れ替えることに注意。

### MLOps
- **一言で**: 機械学習（ML）の開発チームと運用（Ops）チームが連携し、**開発 → デプロイ → 監視 → 再学習** のサイクルを継続的・自動的に回す考え方と仕組み。
- **なぜ生まれたか**: モデルは作れても、本番での運用・更新が属人的で続かないことが多かった。2015年にGoogleの研究者が発表した論文「機械学習システムに潜む技術的負債」は、**機械学習のコードはシステム全体のごく一部にすぎず、データ収集・監視・設定などの周辺の仕組みが大半を占める**ことを指摘し、運用の仕組み化が注目されるきっかけになった。
- **違い**: ソフトウェア開発の **DevOps**（開発と運用の連携）を機械学習に広げたもの。DevOps がコードを管理するのに対し、MLOps は**データとモデルのバージョン管理**、**データの変化の監視**、**再学習の自動化**も扱う。
- **主な要素**: データ・モデルのバージョン管理、学習パイプラインの自動化、テストとデプロイの自動化（CI/CD）、モニタリング、再学習。Docker などのコンテナ技術がよく使われる。
- 生成AI・LLM の運用に特化した考え方を LLMOps と呼ぶこともある。
- **問われ方**: 「MLOps の説明として正しいもの」→ 運用まで含めて継続的に改善する考え方。「モデルを一度デプロイすれば更新は不要」は誤り。

### 人間の関与
- AIの出力をそのまま使わず、確信度が低いものや重要な判断は**人が確認する**（ヒューマン・イン・ザ・ループ）。確認結果を新しい教師データとして再学習に使うこともできる。詳細は → 10章「人間の関与」。

## 7-5 AIの社会実装の事例

試験では個別の企業名より、**「どの分野で、どんなAI技術が、何のために使われるか」**の対応が問われる。

| 分野 | 活用例 | 主な技術 |
|---|---|---|
| 製造 | 製品の**外観検査**（傷・不良の検出）、設備の**予知保全**（故障の前兆検知） | 画像認識、異常検知、IoT・エッジAI |
| 医療 | 画像診断の支援（X線・CT・内視鏡）、創薬 | 画像認識、セグメンテーション |
| 小売・EC | **需要予測**による発注・在庫の最適化、**レコメンド**、無人店舗 | 時系列予測、協調フィルタリング、物体検出 |
| 交通・物流 | **自動運転**、配送ルートの最適化 | 物体検出、センサーフュージョン、強化学習 |
| 金融 | **不正取引の検知**、与信審査 | 異常検知、分類 |
| 農業 | 生育状況の把握、収穫ロボット、ドローンでの散布 | 画像認識、マルチスペクトル画像 |
| インフラ | 橋・トンネル・道路の点検 | 画像認識（ひび割れ検出） |
| 接客・事務 | チャットボット、コールセンターの応対支援、文書作成・要約 | 生成AI（LLM）、RAG、音声認識 |

- **自動運転の動き**: 日本では2023年4月施行の改正道路交通法で、特定の条件下で運転者のいない**レベル4（特定自動運行）**が許可制で可能になり、同年5月に福井県永平寺町で国内初のレベル4の運行が始まった。
- **生成AIの業務活用**: 社内文書を検索して回答させる RAG、議事録の要約、プログラミング支援などが広がった。一方で、ハルシネーション・情報漏えい・著作権への対策が導入の条件になる（→ 06・09・10章）。

## 章末まとめ（暗記必須）

**人物・年号**
- BPR: 1990年代初めにマイケル・ハマーらが提唱
- CRISP-DM: 2000年に公開（1990年代後半に企業連合が策定）／CRISP-ML(Q): 2020年に提案
- MLOps のきっかけ: 2015年のGoogleの論文（機械学習システムの技術的負債）
- 2023年4月 改正道路交通法でレベル4が許可制に／2023年5月 永平寺町で国内初のレベル4運行

**数値**
- AIプロジェクトの要素は **3つ**（AI人材・課題の決定・データの確保）
- CRISP-DM は **6工程**、CRISP-ML(Q) も **6工程**
- MNIST: 手書き数字 **7万枚**（訓練6万・テスト1万）、28×28

**対応関係**
- CRISP-DM の順番: ビジネス理解 → データ理解 → データ準備 → モデリング → 評価 → 展開
- CRISP-ML(Q) の Q → Quality（品質保証）、最後に「監視と保守」
- MLOps ＝ ML ＋ Ops（DevOps の機械学習版）
- 仕様変更に強い → アジャイル／全体管理しやすい → ウォーターフォール
- 学習 → クラウド向き／即応が必要な推論 → エッジ向き
- 入力の分布が変わる → データドリフト／入力と正解の関係が変わる → コンセプトドリフト
- オープンイノベーション ⇔ クローズドイノベーション
- 環境をそろえる → Docker／試行錯誤しながら分析 → Jupyter Notebook／外部から機能を呼ぶ → API

**ひっかけ注意**
- プロジェクトの最初は「データを集める」でも「モデルを作る」でもなく、**課題（ビジネス）の理解**。
- データリーケージは**テスト精度が高く見える**のが特徴。本番で精度が落ちて初めて気づく。
- エッジAIは「プライバシーに有利」。クラウドの方がデータを外に出す。
- MLOps はモデルの「開発手法」ではなく、運用まで含めた**継続的なサイクル**の考え方。
- BPR は既存業務の「部分的な改善」ではなく**根本的な作り直し**。
